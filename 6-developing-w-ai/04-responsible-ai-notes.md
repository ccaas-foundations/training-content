# Responsible Use of AI in Software Development

## Security with GenAI

**The concern:** Public LLMs retain user input. Anything pasted into a public model - source code, schemas, credentials, meeting content, client data - may be stored, logged, and used for future training. There is no retrieval mechanism once it is submitted.

**Why it matters:** In CCaaS environments you will work with call recordings, customer PII, routing logic, and internal architecture. A single paste into the wrong tool can permanently expose proprietary IP or regulated data, with no legal remedy.

**What to look out for / how to prevent it:**
- Never paste proprietary code, credentials, database schemas, or client data into a public LLM
- Know the difference between a public tool (ChatGPT.com) and an enterprise API with a data processing agreement - the terms are not the same
- Treat AI tool selection as a data classification decision, not a convenience decision
- When in doubt, assume the model retains it

### The implicit transmission problem

Pasting code into a chat box is the obvious risk, but IDE-integrated and embedded AI tools can transmit data without any explicit action from the developer. This is arguably the larger exposure because it is invisible and continuous.

**How it happens:** IDE-integrated tools don't just send what you type - they assemble a context window to improve suggestion quality, which can include open tabs, recently viewed files, imported modules, and surrounding code. That entire context is transmitted to the model's server on every request. The developer made no explicit decision to share any of it, and in most cases has no visibility into what was included.

**The key question to ask before installing any AI coding tool:** What does this tool send, to where, under what retention policy, and does your organization have a data processing agreement with that vendor?

With an IDE plugin or embedded tool, the trust boundary is not the prompt box - it is the entire workspace.

## Evaluating GenAI Outputs

**The concern:** AI produces plausible output, not correct output. Early models failed loudly - syntax errors, obvious crashes. Newer models fail silently: code that compiles, tests that pass, and logic that is wrong. In agentic contexts, models have been documented fabricating test results and generating fake data rather than surfacing an error.

**Why it matters:** Silent failures in production CCaaS systems - routing logic, analytics pipelines, data ingestion - can corrupt results for weeks before detection. A test suite that was generated by the same model that wrote the code under test is not a reliable safety net.

**What to look out for / how to evaluate:**
- Actively ask how this code could fail - test with invalid or missing input, consider what happens under load, and think through dependency or network failures; AI-generated code tends to handle the happy path well and ignore edge cases
- Verify package names independently - AI regularly invents packages that do not exist
- Do not treat AI-generated tests as ground truth; check that they are testing behavior, not mocking it away
- For any destructive or irreversible operation - DROP, DELETE, schema migration - require explicit human review, never delegate to an agent
- If an AI tool tells you data is gone, a recovery path won't work, or a system state is a certain way - verify against the actual system before acting on it

## Ethical Use of GenAI

**The concern:** The organization that deploys an AI system owns its outputs. "The model said it" is not a legal, ethical, or professional defense. AI systems reflect the biases and gaps in their training data - and that applies both to models you build on your own data and to third-party models you select and integrate. When you choose a model, you are inheriting its training decisions.

**Why it matters:** In CCaaS, this is concrete. If a call routing model was trained on historical data where certain call types were systematically handled by lower-performing agents - due to staffing patterns, shift assignments, or past discriminatory practices - the model will learn to replicate that pattern. It is not malicious; it is doing exactly what training optimizes it to do. The result is that customers in certain segments get worse service, and the system produces a defensible-looking number that obscures the problem. The same risk applies when selecting a third-party model: if you do not understand how the vendor sourced and filtered their training data, you cannot know what biases you are embedding into your product. A model trained predominantly on one demographic's speech patterns will perform worse on others - in a voice analytics platform, that means less accurate transcription and sentiment analysis for a segment of your customer base, systematically.

**What to look out for / how to prevent it:**
- Before deploying any AI-assisted feature, ask: who could be harmed if this is wrong?
- When training on your own data, audit it for historical patterns that reflect past bias rather than desired behavior
- When selecting a third-party model, review the vendor's model card or documentation for how training data was sourced, filtered, and evaluated for bias - if that documentation does not exist, that is itself a signal
- Build a human escalation path for any AI output that informs a high-stakes decision
- Keep outputs auditable - if you cannot explain why the model returned a result, you cannot defend it

## Other GenAI Risks

**The concern:** A consolidated risk map for development teams: hallucination, silent failure, data exfiltration, dependency confusion, agentic overreach, and skill atrophy. These are not hypothetical - all have documented, costly real-world instances.

**Why it matters:** Each risk has a different blast radius. Hallucination wastes time. A hallucinated dependency name exploited as a supply chain attack can compromise your entire CI/CD pipeline. An AI agent with unconstrained production access can destroy data in seconds.

**What to look out for / how to prevent it:**

| Risk | Signal | Control |
|---|---|---|
| Hallucination | Confident output that cannot be independently verified | Always verify against authoritative sources |
| Silent failure | Code runs, tests pass, output is wrong | Human review proportional to stakes; independent test authorship |
| Data leakage | Sensitive content pasted into public tools, or transmitted implicitly via IDE-integrated tools | Data classification policy before AI access is enabled |
| Dependency confusion | AI suggests a package you don't recognize | Audit every dependency before install; check registry independently |
| Agentic overreach | AI agent with write or delete access to production | Least privilege; environment separation; human approval for irreversible ops |
| Skill atrophy | Team cannot debug without AI assistance | Maintain foundational skills; treat AI as a multiplier, not a replacement |

---

## The Bottom Line

AI is a force multiplier for engineers who understand the domain. The developers who will be most valuable are the ones who can identify where AI is likely to be wrong and fix it when it is. That requires deep foundational knowledge - which is exactly what this cohort is building.

> **The question is never "did the AI write it?" - it is "did you verify it?"**
